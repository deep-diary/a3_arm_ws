# LL-092 — controller_state 参考轨迹有前瞻调度：段时间原点不能按「位置离开起点」定，要用速度峰值锚定

> **日期：** 2026-09-23  
> **产品线：** Edge  
> **环境：** RK3588 lubancat + ROS 2 Humble + joint_trajectory_controller（state_publish_rate=200 Hz）

## 现象

F88 验收要按归一化时间 α=t/T 核对 quintic 速度剖面。第一版以「位置首次偏离起点阈值」的时刻作为段起点 t_origin，在 α=0.1 处测出速度比 **1.348**（理论应为 0.243），早期线性检查也得 1.054，看起来控制器在跑线性——与代码选型矛盾。

## 根因

JTC 发布的 `controller_state`（`/arm_controller/controller_state`）里的 **reference 是前瞻量**：控制器为保证跟踪，内部参考轨迹提前于实际运动调度，且段是在 goal 到达时（而不是实际物理开动时）就进入采样。用「位置越过一个小阈值」检测起点，阈值穿越实际发生在 quintic 的 **α≈0.13**（前 13% 位移累积很慢），于是估出的原点比真实原点晚约 0.13T：

- 名义 α=0.1 的采样窗实际落在真实 α≈0.23，quintic 比值 ~1.0；
- 再叠加窗内平均，得到 1.35 这类假比值。

固定 sleep、固定时钟对齐都有同样的偏差源（goal 处理时刻本身也有抖动）。

## 正确做法 / 规避

1. 用 quintic 剖面的**对称不变量**锚定原点：速度峰值严格出现在真实 α=0.5，故  
   `t_origin = t(速度峰值) − T·0.5`。  
   峰值时刻用全段样本最大值定位，200 Hz 采样下误差 ≤2.5 ms（≤0.001T）。
2. 锚定后所有 α 取窗用对称半宽（±12 ms ≈ 2–3 个样本取中值），避免单点抖动。
3. 一般原则：对带前瞻/滤波的参考信号做时间分析时，不要用「阈值穿越」定原点，优先用剖面的对称点、峰值或过零点反推；阈值穿越只适合证明「发生了」，不适合测量「何时开始」。
4. 验收剖面要同时报多个 α 的比值互相印证（0.05/0.1/0.5 + 首尾），单一判据容易被错误原点伪造通过或错误判死。
